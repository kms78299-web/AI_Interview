# 면접 피드백 진행 방향과 데이터 전달 규약

작성: 2026-11-22 · 문서 상태: 팀 공유 초안 · 제안 계약 버전: 1.0

대상: 민서(모델), 지현(백엔드·프론트엔드). 사용자 결정, 민서가 전달한 API 안내, 아직 합의할 제안을 구분한다. **문서 추가만으로 실행 코드나 API가 변경되지는 않는다.**

## 1. 제품 방향 — 사용자 결정

- 숫자 점수·백분위·점수 그래프를 화면에서 제거한다. 필요한 모델 수치는 내부 비교용으로만 유지한다.
- **전반적인 평가는 상·중·하로 제공하고 판단 이유를 함께 보여준다.**
- 질문 5개의 답변 내용은 각각 확인한다. 질문 적합성·구체성·확인 가능한 정확성을 평가한다.
- 음성·영상 평가는 5개 답변을 함께 검토한 **종합 평가 하나**로 제공한다.
- 종합 피드백의 근거는 모든 영상에 하나씩 붙이는 대신, 전체 영상에서 특징이 가장 잘 나타나는 대표 구간을 선택한다. 핵심 피드백별로 서로 다른 영상에서 선택해도 된다.
- 약 3초짜리 짧은 근거 장면이 목표다. 다만 문장 구간 길이가 다를 수 있으므로 재생 종료 정책은 8장에서 별도 제안한다.

**표시 범위 제안:** 첫 버전은 세션 전체 `overall_band` 하나만 표시한다. 질문별·음성별·영상별 추가 등급은 만들지 않는다. 상·중·하 제공은 사용자 결정이며, 구체적인 기준과 이 표시 범위는 팀 합의 대상이다.

## 2. 정보 출처와 현재 확인 상태

### 저장소에서 확인한 현재 구현

- 기준 커밋: `5ce057c` (`main`). 문서 작성 시 `origin/main`도 같은 커밋이다.
- `backend/main.py`: 녹화 저장, STT·분석 호출, 결과 저장·조회, 영상 조회를 제공한다.
- `model/code/serve_gradio.py`: `/stt`와 4개 인자의 `/analyze`를 제공한다. 영상·대본·질문 리스트는 순서로 연결한다.
- 현재 백엔드는 `/analyze`의 `questions_json`에 빈 문자열을 보낸다. 질문별 평가를 위해 실제 질문 원문 5개를 전달해야 한다.
- 모델 결과는 `session`, `videos`, `explanation` 구조이고, 답변별 `stats`, `llm_prompt`가 포함될 수 있다. 백엔드는 아직 LLM을 호출하지 않는다.
- 현재 `extract_stats.py`의 LLM 프롬프트는 답변 한 개 단위다. 기존 `overall_band`도 답변 단위이므로 새 세션 전체 등급과 구분한다.

### 민서에게 전달받은 구간별 API 안내 — 저장소 미반영 명세

다음은 사용자가 전달한 안내를 옮긴 것이다. 작성 시 저장소 코드에서 확인한 구현으로 간주하지 않는다. 민서의 변경이 올라오면 `model/API.md`의 ‘구간별 피드백’과 실제 응답으로 대조한다.

1. `/stt` 대신 **`/stt_segments`**를 호출하면 영상마다 `{text, segments}`를 받는다.
2. 각 문장 구간은 `id`, `start`, `end`, `text`를 가진다. 화면 대본은 상위 `text`를 그대로 쓴다.
3. `/analyze`의 **5번째 인자 `segments_json`**에 영상 순서대로 구간 목록을 담은 리스트를 넣는다.
4. 결과의 `videos[i].segments`에 구간별 측정값, `markers`, `rule_flag`가 온다. 기존 4개 인자 호출도 유지된다.
5. Gemini 응답에 `evidence`(근거 구간 ID 목록)가 추가된다. 존재하지 않는 구간 ID는 버린다.
6. 개선 구간: `rule_flag == "issue"`이거나 Gemini가 `improvement`로 인용한 구간.
7. 좋은 구간: Gemini가 `strength`로 인용했고 `issue`가 아닌 구간.
8. 답변당 좋은·개선 구간을 각각 1~2개만 보여준다. 문장·카드를 누르면 `start - 1초`부터 재생한다.

아직 전달되지 않은 세부 사항: `/stt_segments` 응답의 최상위 포장 형식, ID 자료형·유일성 범위, 구간 측정값의 정확한 필드, `markers`의 타입, `rule_flag`의 전체 값, Gemini `evidence`가 강점·개선점과 연결되는 정확한 JSON 모양. 아래 예시 중 해당 부분은 **제안**이며 실제 지원 필드라고 가정하지 않는다.

## 3. 역할 분담과 전체 흐름

| 담당 | 수정 범위 | 넘겨줄 결과 |
| --- | --- | --- |
| 지현 | 세션·질문·영상 저장, `/stt_segments` 호출·캐시 | 질문 ID·질문·대본·문장 구간 5개 묶음 |
| 민서 | 모델·Gradio 수정, 구간 측정·마커, 상대 비교·occlusion 검증 | `videos[i].segments`, 분석 상태, 내부 비교 결과 |
| 공동 | Gemini 호출 위치·세션 프롬프트·등급·evidence 구조 합의 | 질문별 내용 5개 + 종합 평가 하나의 출력 계약 |
| 지현 | 응답 정규화·검증·저장·영상 연결 | 화면용 피드백과 유효한 구간 참조 |
| 지현 | 점수 제거, 상중하·내용 카드·종합 피드백·구간 재생 | 예시 데이터로 먼저 동작하는 UI |

```text
녹화 5개 + 질문 원문
 → /stt_segments: 전체 text + 문장 segments
 → /analyze: 영상·대본·질문·with_stats·segments_json
 → 구간별 관찰·마커·rule_flag
 → Gemini: 질문별 내용 + 세션 종합 상중하·피드백 + 근거 구간 ID
 → 백엔드: 참조 검증·구간 라벨 결정·대표 장면 선택·영상 URL 연결
 → 화면: 내용 5개 / 종합 평가 1개 / 대표 장면
```

Gemini 실행 위치는 안내만으로 확정할 수 없다. 민서 쪽에서 호출하면 지현은 반환값을 검증·저장한다. 백엔드가 호출하기로 하면 민서의 분석 결과를 받아 동일한 출력 계약으로 요청한다. **중복 호출하지 않는다.** 기존 답변별 Gemini 호출을 유지하더라도 마지막 종합 평가는 5개 답변 자료를 함께 검토해야 한다.

## 4. ID·시간·자료 부족 공통 규칙 — 연결 계약 제안

- 답변은 현재 앱과 같은 `session_id` + `question_id`로 식별한다. 새 `answer_id`는 만들지 않는다.
- 문장 구간 참조는 **`question_id` + `segment_id`** 쌍을 사용한다. 서로 다른 영상에서 `id=1`이 겹칠 수 있으므로 ID만으로 전체 세션에서 찾지 않는다.
- 원본 구간의 `id` 값·자료형은 보존한다. LLM 출력도 같은 자료형을 사용한다. `1`과 `"1"`을 임의로 섞지 않는다.
- 시간은 각 질문 영상 시작이 0인 초 단위다. `0 <= start < end <= duration_sec`이며 유한 숫자여야 한다. 원격 분석 임시 파일 경로는 재생 주소가 아니다.
- 기존 Gradio가 질문 ID를 받지 않으면 백엔드가 요청 순서 ↔ 질문 ID를 보관하고 `videos[i]`와 연결한다. 순서·개수가 틀린 응답은 연결하지 않는다.
- 재녹화·대본 변경·재분석 시 구간 ID와 피드백이 낡지 않도록 같은 분석 묶음으로 교체한다. 이전 분석의 구간 ID를 재사용하지 않는다.
- 답변 하나가 실패해도 나머지 내용 평가는 유지한다. 실패·빈 대본·모델 제외는 상태와 이유로 구분한다. 자료 부족을 ‘하’나 임의의 ‘중’으로 바꾸지 않는다.

## 5. 단계 A — STT와 분석 요청

### STT 결과

아래는 영상 한 개의 개념 예시다. 실제 최상위 리스트·객체 구조는 민서 응답을 확인해 맞춘다. 모든 예시는 가상 데이터다.

```json
{
  "text": "I study software engineering. I enjoy working with a team.",
  "segments": [
    {"id": "s1", "start": 0.8, "end": 3.2, "text": "I study software engineering."},
    {"id": "s2", "start": 5.3, "end": 8.0, "text": "I enjoy working with a team."}
  ]
}
```

- 화면에는 `text`를 그대로 표시하고, 문장 클릭 기능은 별도로 `segments`와 연결한다. 구간 텍스트를 다시 합쳐 원문을 덮어쓰지 않는다.
- 캐시는 전체 text와 segments를 함께 보관한다. 과거 `/stt` 텍스트 캐시만으로 문장 시간이 있다고 간주하지 않는다.
- `/stt_segments`가 배포되지 않았거나 실패하면 구간 기능 불가를 표시한다. 더미 시간으로 대체하지 않는다. 기존 `/stt`를 쓰는 경우 전체 대본만 제공하고 해당 상태를 명시한다.

### `/analyze` 호출 순서 — 민서 안내 기준

```python
client.predict(
    files,             # 영상 5개, 질문 순서
    transcripts_json,  # 각 영상의 전체 text를 담은 문자열 리스트의 JSON
    questions_json,    # 같은 순서의 실제 질문 원문 5개 리스트의 JSON
    True,              # with_stats
    segments_json,     # 같은 순서의 segments 리스트 5개를 담은 JSON
    api_name="/analyze",
)
```

`segments_json`은 `[[{id,start,end,text}, ...], [...], [...], [...], [...]]` 구조다. 일부 영상의 구간이 없을 때 `[]`를 허용하는지 민서와 확인하고, 지원 전에는 분석 가능한 입력으로 조용히 변환하지 않는다. 기존 4개 인자 방식은 구간 기능 없는 호환 경로로 유지한다.

## 6. 단계 B — 모델 응답과 Gemini 입력

민서는 영상 순서에 맞는 `videos[i].segments`를 반환한다. 구간의 원래 ID·시간·텍스트가 유지되어야 한다. 측정값·markers·rule_flag의 구체적인 구조는 실제 응답으로 확정한다. 지현은 임의의 지표 이름이나 `rule_flag` 값을 추가하지 않는다.

세션 종합 Gemini 입력에는 다음이 필요하다.

| 자료 | 목적 |
| --- | --- |
| 세션 ID, 질문 ID·원문·순서 5개 | 어떤 질문에 대한 답변인지 판단 |
| 전체 대본 `text` 5개 | 질문별 내용 평가 |
| 문장 구간 ID·시간·텍스트 | 근거 구간 인용 |
| 구간별 측정값·마커·rule_flag와 유효성 정보 | 확인된 음성·영상 관찰 설명 |
| 답변별 전체 관찰, 분석 누락·실패 이유 | 종합 평가와 제한 사항 |
| 내부 상대 비교 결과(지원·검증된 경우) | 비교할 답변 또는 대표 장면 후보 탐색 |

내부 `raw` 점수와 백분위·기존 모델 등급을 세션 상중하로 자동 변환하지 않는다. 같은 사람의 답변 비교가 유효한지, 어떤 항목을 비교할지, 구분이 어려울 때 유보할지는 민서 검증이 필요하다. 상대 비교는 좋은 관찰 후보를 찾는 보조 자료이며 내용 정확성을 대신 판단하지 않는다.

Occlusion 결과는 우선 ‘모델이 반응한 구간’이다. 그 자체만으로 ‘실제로 못한 구간’ 또는 ‘시선이 불안정함’을 단정하지 않는다. 시선·쉼 등 구체적 설명에는 해당 관찰 자료가 필요하다. 기존 모델이 전체 데이터에서 보인 Spearman 성능이 동일인 답변 5개나 3초 구간 순위를 보장하는 것은 아니다.

## 7. 단계 C — Gemini 최종 출력 제안

아래는 **종합 평가 화면을 위한 새 정규화 계약 제안**이다. 민서의 기존 Gemini `evidence` 형태가 확인되면 이 구조로 바로 출력하거나 백엔드 어댑터에서 변환한다. 현재 API가 이미 이 형태라는 의미는 아니다.

완전한 가상 예시: [examples/session-feedback.example.json](examples/session-feedback.example.json). 질문별 결과 5개를 포함한다.

| 필드 | 형식·의미 |
| --- | --- |
| `schema_version`, `session_id` | `"1.0"`, 요청 세션 ID |
| `status` | `ready` / `partial` / `insufficient_data` |
| `overall_band` | 세션 전체 `상` / `중` / `하` / `null` |
| `band_reason`, `summary` | 등급 이유, 전체 요약 |
| `answer_feedback` | 입력 질문 ID와 일치하는 정확히 5개 결과 |
| 문항별 `status` | `evaluated` / `insufficient_data` |
| 문항별 `relevance` | `{rating, reason}`. rating: `적절` / `부분적` / `부적절` / `평가불가` |
| 문항별 `specificity` | 구체성 설명 |
| 문항별 `accuracy` | `{status, reason}`. status: `supported` / `contradicted` / `unverified` |
| 문항별 `strength`, `improvement` | 내용 피드백. 자료 부족 시 `null` |
| `delivery_feedback` | 세션 전체 객체 하나. `summary`, `strengths`, `improvements` |
| 전달 피드백 항목 | `modality`, `feedback`, `suggestion`, `scope`, `related_question_ids`, `evidence` |
| 항목의 `evidence` | `[{question_id, segment_id}, ...]`. 강점 배열 안에서는 strength 인용, 개선점 배열 안에서는 improvement 인용 |
| `limitations` | 자료 누락·인식 한계 등 문자열 배열 |

LLM 작성·검증 규칙:

1. 숫자 점수·백분위는 만들지 않는다. 상중하는 세션 전체 코칭 판단으로 이유와 함께 제공한다. 모델의 `scores.*.band`와 구분한다.
2. 문항별 내용 결과는 5개를 유지한다. 빈 대본이면 평가 불가와 이유를 쓰고 강점·개선점은 `null`로 둔다.
3. 사실 정확성은 질문 적합성과 구분한다. 자기소개 경험담의 진위는 대본만으로 확인하지 않는다. 확인 자료가 없으면 `accuracy.status=unverified`다. 자료를 추가하기 전 첫 버전에서는 이를 기본으로 한다.
4. 음성·영상은 5개를 검토한 종합 평가로 쓴다. `scope=single_answer`는 관련 질문 1개, `multiple_answers`는 2개 이상이다. 문장으로도 관찰 범위를 밝힌다.
5. 여러 답변의 특징이라고 쓸 때는 해당 질문들에 실제 관찰 자료가 있어야 한다. 대표 영상 한 개만으로 전체 경향을 주장하지 않는다. 원본 관찰은 백엔드에서 검토 가능하게 보존한다.
6. `evidence`는 제공된 구간 ID만 인용한다. 시간·URL·구간 ID를 생성하지 않는다. 근거가 없으면 빈 배열을 쓴다. 없는 ID는 민서 안내대로 버리되 로그에 남긴다. 단, 소속이 모호한 ID를 임의의 영상으로 연결하지 않는다.
7. 전달 피드백 강점·개선점은 각각 0~2개를 초기 제안으로 한다. 근거를 억지로 채우지 않는다. 감정·성격·합격 가능성을 추측하지 않는다.
8. JSON 객체 하나만 출력한다. 설명 문장·코드 블록은 붙이지 않는다. 기본 언어는 한국어다.

### 상·중·하 기준 초안 — 팀 합의 대상

| 등급 | 의미 |
| --- | --- |
| 상 | 대부분의 답변이 질문에 직접 답하고 구체적이며, 확인된 전달 관찰에서도 핵심 내용을 이해하는 데 큰 방해가 적음 |
| 중 | 대체로 질문에 답하지만 구체성이나 전달 방식에서 보완할 점이 있음 |
| 하 | 여러 답변에서 질문에 충분히 답하지 못하거나, 핵심 내용을 전달하는 데 큰 보완이 필요함 |
| null | 자료 부족으로 종합 판단이 어려움. 낮은 평가를 뜻하지 않음 |

짧은 답변, 한 번의 시선 이탈, 특정 목소리 특성만으로 ‘하’를 주지 않는다. `insufficient_data`이면 등급은 `null`, `ready`이면 등급이 있어야 한다. 일부만 분석된 `partial`의 등급 제공 조건은 합의가 필요하다. 우선 자료 부족의 이유와 평가 가능한 부분을 표시하고 무리한 전체 판단을 유보한다.

## 8. 구간 라벨과 대표 장면·재생 정책

### 민서 안내의 구간 분류 규칙

```text
valid_improvement_refs = 유효한 improvement 인용
valid_strength_refs    = 유효한 strength 인용
is_issue               = segment.rule_flag == "issue"

개선 구간 = is_issue OR improvement 인용됨
좋은 구간 = strength 인용됨 AND NOT is_issue
```

- 같은 영상·같은 ID의 중복 인용은 제거한다. 없는 ID·잘못된 시간은 제외한다.
- `issue`인 구간은 strength로 인용돼도 좋은 구간으로 표시하지 않는다.
- `issue`가 아니면서 양쪽에 인용된 구간은 위 식상 두 조건을 만족한다. UI 중복을 막기 위해 **개선 라벨 우선**을 제안하며, 이 충돌 정책은 민서와 확인한다.
- 답변별 상세 화면을 만들 경우 각각 1~2개가 **상한**이다. 후보가 0개면 채우지 않는다. 여러 개일 때 선택할 순서·우선순위는 합의해야 하며 임의로 ‘가장 좋음’이라고 부르지 않는다.

### 사용자 방향과 연결하는 화면 제안

- 메인 결과: 질문별 내용 5개 + 세션 전체 등급·종합 피드백 하나. 전달 피드백별 **대표 장면 한 개**를 전체 5개 영상의 유효 근거 중에서 선택한다.
- 답변별 좋은·개선 구간 1~2개는 상세 대본의 선택 기능으로 둘 수 있다. 모든 답변에 별도 음성·영상 평가 카드를 만드는 의미는 아니다.
- 이 상세 화면은 민서가 제안한 표시 방식이며, 현재 사용자가 확정한 메인 화면 요구와 구분한다. MVP는 메인 종합 피드백과 대표 장면을 먼저 구현한다.
- 대표 근거는 해당 피드백의 관련 질문 집합 안에서 선택한다. 여러 문장 근거가 있으면 실제 관찰이 명확한 구간 하나를 고르는 기준이 필요하다. 이를 위한 우선순위 필드·선택 책임은 팀 합의 대상이다.

### 재생

- 시작은 민서 안내대로 `max(0, start - 1.0)`이다. 영상 URL은 백엔드가 현재 영상 조회 API로 만든다.
- 문장·대본 클릭은 해당 문장의 `end`까지 재생하는 방식을 제안한다.
- 대표 장면 카드는 시작부터 약 3초 뒤에 멈추는 미리보기를 제안한다. 단, 긴 문장이 잘리거나 근거 행동이 늦게 나오면 3초 안에 특징이 안 보일 수 있다. 그 경우 원문 구간 끝까지 재생할지 또는 별도 짧은 구간을 받을지 확인해야 한다.
- **약 3초 목표와 문장 전체 재생은 동일하지 않다.** 종료 시점 정책은 아직 확정하지 않고 UI·모델이 같은 값으로 합의한다. 합의 전에는 `start - 1초`부터 문장 `end`까지 재생하는 경로를 기준 예시로 사용한다.
- 원본 영상을 seek하고 멈추는 방식으로 먼저 구현한다. 별도 클립 파일 생성은 필수가 아니다.

## 9. 단계 D — 백엔드 → 화면

정규화 피드백과 사용되는 구간만 포함한 `evidence_segments` 배열을 반환하는 방식을 제안한다. 다음은 배열 원소 한 개다.

```json
{
  "question_id": "introduction",
  "segment_id": "s2",
  "start": 5.3,
  "end": 8.0,
  "playback_start": 4.3,
  "playback_end": 8.0,
  "label": "improvement",
  "video_url": "/api/interviews/demo_session/answers/introduction/video"
}
```

- `start/end`는 원래 분석 구간이며 재생 편의를 위한 `playback_start/end`로 덮어쓰지 않는다. 재생 값은 백엔드가 검증·생성한다.
- 대표 구간만 버튼으로 제공하고 추가 근거는 필요 시 펼쳐 볼 수 있게 한다. 자동 대표 선택이 아직 없으면 예시 데이터에서 수동 지정하되 실제 자동 결과로 표시하지 않는다.
- 유효 근거가 없으면 버튼을 숨기고 본문은 유지한다. 영상 재생 실패는 피드백 생성 실패와 구분한다.
- 프론트에는 모델 raw·백분위·모델 점수 band 대신 LLM `overall_band`를 표시한다.
- `partial`·등급 `null`이면 제한 사항과 확인 가능한 피드백은 유지한다.

## 10. 저장·실패·호환

- 새 계약은 기존 `result.json`과 구분해 버전별로 저장하거나 별도 `feedback_v1.json`에 저장하는 방식을 제안한다. 새 조회 엔드포인트는 구현 때 확정한다.
- 기존 모델 응답 검증을 바로 없애지 않는다. 기존 점수 응답을 내부에 유지해도 UI의 점수는 제거할 수 있다.
- 백엔드는 세션·질문 5개 일치, ID 중복·누락, enum, JSON 형식, 영상 길이·시간, 근거 소속, 상태와 등급의 일관성을 검사한다.
- 존재하지 않는 Gemini evidence ID는 **버리고 기록**한다. 모두 사라지면 근거 버튼 없이 반환한다. 피드백의 내용 자체도 관찰로 뒷받침되지 않으면 재생 버튼 제거만으로 충분하지 않으므로 재생성 또는 평가 유보 처리한다.
- 세션 불일치·필수 질문 누락·깨진 JSON은 유효 결과로 저장하지 않는다. 재시도 후 실패를 표시하며 더미 결과로 자동 대체하지 않는다.
- 구간 인식 실패와 낮은 평가를 구분한다. 새 녹화의 구간을 이전 결과에 연결하지 않는다.
- 예시 모드는 `is_dummy=true`로 명시한다. 실제 대본·영상·환경 파일을 Git에 올리지 않는다.

## 12. 민서에게 받을 것과 지현이 넘길 것

**민서에게 받을 것**

- `/stt_segments`·5개 인자 `/analyze`가 실제 배포된 주소 또는 코드 커밋.
- 새 `model/API.md`와 영상 5개에 대한 비식별 예시 응답. 실제 개인 영상은 필요하지 않다.
- 구간 `id` 타입·유일성 범위, 측정값·markers·rule_flag enum, 일부 구간 누락 시 처리 방식.
- Gemini evidence의 정확한 JSON과 strength/improvement 연결 방식, 현재 답변별 호출인지 세션 호출인지.
- 구간 후보가 여럿일 때 우선순위·대표 선택 방법. 상대 비교·occlusion은 검증 상태도 함께.

**지현이 넘길 것**

- 실제 질문 원문·질문 ID·순서, 녹화와 STT 구간이 일치하는 입력 묶음.
- 이 문서의 정규화 출력 제안과 가상 예시, UI가 필요로 하는 필드.
- 세션 전체 상중하 기준·LLM 호출 위치·재생 종료·상세 화면 범위에 대한 공동 합의 결과.

이 문서의 미합의 항목은 구현 책임과 연결 형식을 맞추기 위한 것이다. 이미 정한 ‘점수 제거·상중하 제공·내용 5개·음성영상 종합 평가’ 방향을 되돌리는 항목은 아니다.
